## Deploying alongside WordPress

WordPress does not need to be deleted. Apache loads `index.php` before
`index.html`, which is the only reason WordPress keeps winning at `/`.
One line flips that:

```apache
DirectoryIndex index.html index.php
```

Put it at the top of the existing `public_html/.htaccess`, above the
`# BEGIN WordPress` block, and leave that block alone. The static homepage
serves at `/`, WordPress stays installed, `/wp-admin/` still works, and
deleting that one line reverts everything.

Use `htaccess-merge-snippet.txt` rather than this repo's `.htaccess` while
WordPress is present — the full file strips `www.`, which deadlocks against
WordPress's own canonical redirect if the WP Site URL uses `www`.

## Header

- Sticky, translucent, blurred backdrop.
- Desktop: logo left, nav centre-right, "Get It Now" pill right.
- Mobile (≤860px): nav collapses to a hamburger that opens a dropdown panel.
- Light and dark mode, following the OS setting.
- Keyboard accessible: skip link, visible focus rings, Escape closes the menu,
  `aria-expanded` reflects state.
- Degrades without JavaScript — the nav stays visible rather than becoming unreachable.

Nav labels and links live in the `<nav id="primary-nav">` block in `index.html`.
The CTA points at `#get-it-now`; change the `href` once there's a real target.

## Editing and building

`src/index.html` is the source of truth. The deployed `index.html` at the
repo root is **generated** from it and should never be hand-edited.

```bash
npm install     # once
npm run build   # src/index.html -> index.html
```

The build minifies the inline CSS (clean-css) and JS (terser), compacts the
JSON-LD, strips comments and collapses whitespace. It fails loudly if
anything load-bearing goes missing.

Always run the build before committing, or the deployed page will be stale.
